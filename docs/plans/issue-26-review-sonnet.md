# issue #26 プランレビュー（3案比較・Sonnet 独立レビュー）

対象: `docs/plans/issue-26-plan-opus.md` / `issue-26-plan-gpt.md` / `issue-26-plan-grok.md`
レビュー方針: 各プランの作成者ではなく第三者として、issue 本文・`CONTEXT.md`・ADR・実コードに照らして判定する。忖度しない。

## 0. 前提として確認した事実（コード検証）

レビューの根拠になった、コードを実際に読んで確認した事実を先に挙げる。

1. **本番の秘密情報の経路は「app は常に ENV を読む。Kamal が credentials から ENV へ注入する」で統一されている。** `config/initializers/omniauth.rb` は `ENV["GOOGLE_CLIENT_ID"]` を直読みし、`.kamal/secrets` が `$(bin/rails credentials:fetch google.client_id)` で ENV へ詰め替えている。dev/test は `.env` + dotenv-rails。**`Rails.application.credentials` をアプリコードから直接読んでいる箇所は現状ゼロ**（`config/storage.yml` と `production.rb` の SMTP 設定はいずれもコメントアウト）。
2. **`config/master.key` はリポジトリに存在せず、`.gitignore` の `/config/*.key` で追跡対象外。** CI ワークフロー（`.github/workflows/ci.yml`）にも `RAILS_MASTER_KEY` を渡す設定が一切無い。`config/credentials.yml.enc` は環境別ファイルに分かれておらず単一ファイルなので、**鍵が無い状態で `Rails.application.credentials` に触れると起動時（`config/application.rb` 相当のロード時）に復号が走り、CI・鍵を持たない開発クローンの `bin/rails` 系コマンド全般が壊れる。**
3. `require_login` は `ApplicationController` にあり、`HistoriesController` / `AchievementsController` / `BattlesController` など複数の呼び出し元を既に持つ共有フィルタ。「ApplicationController に認可フィルタを置く」設計は本リポジトリの既存パターンそのもの。
4. `Ranking.tsx` は `router.get(..., { only: ['entries'] })` の部分リロードを実際に使っている（59–63行目）。`History.tsx` は `formatDate` をローカルに持つのみで共通化されていない。
5. `Feedback` に `has_many :feedbacks` の逆関連は無く、`User` にも `admin?` 相当のメソッドは無い。`docs/design/design.pen` に「管理者」「admin」に一致するノードは無い（grep 0件）。
6. `CONTEXT.md`「フィードバック」の定義文はすでに「運営」という語を使っている（「プレイヤーがアプリ内フォームから**運営**へ送る連絡」）。glossary の項目としての「運営」「管理者」はどちらも未収載。issue のタイトルは「管理者用」。

これらは3プランの対立点の判定に直結する。

## 1. 総評

3プランとも issue の核（読み取り専用一覧・認可・存在の扱い）は正しく捉えており、致命的な誤読は無い。ただし技術的な妥当性には無視できない差がある。

- **Opus 案**は最も保守的で、既存コードの慣習（ENV 経路、`ApplicationController` の共有フィルタ、`Ranking.tsx` の部分リロード地雷）を実際に検証した跡があり、リスクテーブルが具体的。ドメイン用語の矛盾（管理者 vs 運営）にも正面から答えを出している。分量は最も多いが、水増しではなく判断の根拠を積んでいる。
- **GPT 案**は認可を `Rails credentials` 直読みに置く設計を採用しており、**これは本リポジトリの既存の秘密情報の流儀と食い違うだけでなく、`config/master.key` を持たない CI・開発クローンで起動を壊す実害のある欠陥**。存在隠蔽についても「トップへ 302 + 権限不足メッセージ」を選んでおり、レビュー観点として明示された「存在隠蔽」を実質満たしていない。`Admin::BaseController` を最初の管理ページ 1 枚のために新設するのも投機的。
- **Grok 案**は認可モジュールの切り出し方（`AdminAccess` という薬POROを`User`から分離する発想）に見るべき点があるが、「ページネーション無し・全件返す」という決定は issue の「埋もれ解消」という目的をむしろ将来にわたって再生産するリスクの評価が甘く、`has_many :feedbacks, dependent: :nullify` を本 issue についでに混ぜるのはスコープ外の変更を持ち込んでいる（Opus は同じ論点を発見しつつ「別issueへ」と切り離しており、その判断の方が規律がある）。「管理者」の用語問題を認識しながら解決を放棄している点も、`domain-modeling` スキルの「既存語との矛盾は先送りせず解消する」という指針に沿っていない。

総じて **Opus 案をベースに採用し、GPT 案の props allowlist の厳密さと no-store ヘッダの発想、Grok 案の「AdminAccess を独立モジュールにする」発想の一部を取り込む**のが最も安全な合成になる（詳細は§4）。

## 3. 対立点ごとの判定

### 3.1 秘密情報の出どころ: ENV（Opus・Grok） vs credentials 直読み（GPT）

**判定: ENV を採用。GPT 案は却下。**

GPT 案は `config/application.rb` で `Rails.application.credentials.dig(:admin, :emails)` を起動時に正規化する設計。しかし §0-2 で確認したとおり、`config/master.key` は本リポジトリに存在せず CI にも渡っていない。GPT 案を実装すると、**この管理者一覧機能と無関係な既存の CI ジョブ（`backend_test` の `db:test:prepare` / `bundle exec rspec`、`scan_ruby` の `brakeman`）まで鍵不足で落ちる可能性が高い。** さらに新規開発者がクローンした直後、`config/master.key` を持たない限り `bin/rails` すら通らなくなる。これは GPT 案自身が却下している「ADMIN_EMAILS を Kamal secret に追加する」案への反論（「credentials に集約する方針と矛盾する」）よりずっと重大な、実行可能性そのものの問題である。GPT 案はこの矛盾を検証しておらず、既存の OAuth クレデンシャルの配線（`ENV["GOOGLE_CLIENT_ID"]` 方式）も見落としている。

Opus・Grok は共に ENV 優先（Grok は ENV → credentials フォールバックの二段構えだが、実質は ENV 経路が主）。Opus の方が「なぜ ENV か」を既存コードの参照付きで説明しており、実装時の迷いが少ない。**Opus の「常に ENV を読み、本番は Kamal が credentials から注入する」を採用する。**

### 3.2 認可判定の置き場所: `User#admin?`（Opus） vs `Admin::BaseController`（GPT） vs `AdminAccess` PORO（Grok）

**判定: Opus の `User#admin?` + `ApplicationController#require_admin` を採用。`Admin::BaseController` は却下。`AdminAccess` は次点。**

`codebase-design` スキルの「1つのアダプタは仮の seam、2つ目で本物の seam になる」という原則に照らすと、管理ページが 1 枚しか無い現時点で `Admin::BaseController` を新設する GPT 案は投機的な抽象化（Middle Man の一種）。継承階層は「サブクラスが増えてから抽出する」で十分に安く後から作れるので、今作る理由が薄い。Opus・Grok 自身もこの判断を明示的に却下案として書いており、GPT だけがこれを採用している。

`User#admin?` と `AdminAccess.granted?(user)` はどちらも「小さい述語・fail closed をモジュール内部に隠す」という点で深いモジュールの条件を満たし、実装として大きな優劣は無い。判定基準は**既存コードの慣習との整合**に置く。`require_login` は既に `ApplicationController` にあり、`HistoriesController` / `AchievementsController` / `BattlesController` の3箇所から呼ばれている共有フィルタの実例がある。`require_admin` を同じ場所に置く Opus 案は、この既存パターンに一致する最小差分。Grok の `AdminAccess` を導入する動機（「運用フラグをプレイヤー集約の `User` に混ぜたくない」）自体は理解できる設計上の立場だが、コード識別子は既にドメイン語彙と分離してよいという前例（`walkover` コード識別子・部屋のコード表記）を CONTEXT.md 自身が認めているため、`admin?` という英語識別子を `User` に置くこと自体はこのリポジトリの流儀の範囲内であり、Grok の反対理由はやや強すぎる。**Opus 案を採用し、`AdminAccess` は「将来 `User#admin?` を差し替える必要が出たときの移行先候補」として記録に残す。**

### 3.3 非運営への応答: 常に404（Opus） vs ゲスト302+一般ユーザー302+flash（GPT） vs ゲスト302・一般ユーザー404（Grok）

**判定: Opus の「運営以外は常に404（未ログインもログイン済み一般ユーザーも同じ）」を採用。GPT 案は却下、Grok 案は次点。**

これはレビュー観点で明示された「存在隠蔽」に最も直結する対立点。GPT 案は非管理者ログインユーザーをトップへ 302 + 「権限不足」flash で返す。これは実質的に「このページは存在し、あなたには権限が無い」と教える応答であり、`CONTEXT.md`「フィードバック」の定義がそのまま要求する認可要件（「送信内容は公開されず、他のプレイヤーからは見えない」）を HTTP レベルで弱めている。GPT 案自身は「クライアントだけで isAdmin を隠す、または URL を秘匿するのは却下する」と書いているが、これは論点のすり替えである。批判対象にしているのはクライアント側の表示制御であり、レビューが問題にしているのは**サーバのレスポンスそのものが権限の有無を区別してしまう**ことであって、GPT 案はこの後者を実際にやっている。

Opus と Grok はどちらも「ログイン済み非運営」には 404 を返す点で一致し、この部分は正しい。差は「未ログイン（ゲスト）」の扱いで、Opus は 404 に統一し、Grok は他の `require_login` ページと同じ `/auth/login` への 302 にする。Grok の理由（「運営が未ログインで開いたとき迷わないように」）は UX として理解できるが、この一覧ページはヘッダーにもリンクを出さない（3案とも同意）以上、運営は日常的に既にログイン済みの状態でこの URL を叩く運用になるはずで、未ログイン時の 404 で迷うコストは低い。一方で **判定コードパスを1つに統一できる**（「運営かどうか」だけを見る1つの `before_action`。ログイン状態で分岐しない）ことのテスト容易性・実装単純性の利得は実質的。**Opus 案（常に404）を採用**するが、これは僅差の判定であり、Grok 案（ゲストのみ302）を採用しても実害は小さいことは記録しておく。

### 3.4 ページネーション: サーバ側ページング（Opus・GPT） vs 全件返却・ページング無し（Grok）

**判定: サーバ側ページングを採用。Grok の「全件返却」は却下。**

Grok 案は却下理由として「History 方式（最新50件・ページ送り無し）は古い件に到達できず issue の『埋もれ』を再発する」を挙げているが、これは Opus が同じ理由で明確に区別している**「上限付き・ページ送り無し」と「ページネーション（上限はあるが全件に到達できる）」の違いを混同している。** ページネーションは全件への到達性を損なわない。Grok の却下理由はサーバ側ページング自体には当てはまらない。

「全件を1レスポンスで返す」設計は、件数が増えるほど単調に劣化する（レスポンスサイズ・レンダリング量が無制限）。現状のフィードバック件数は少ないため今すぐ壊れるわけではないが、issue が解決したい「運営が確認しにいく」運用を軌道に乗せるほど件数は増えていく設計であり、「今は小さいから無制限でよい」という前提はこの機能の目的とやや矛盾する。**Opus・GPT のサーバ側ページング（50件/ページ・`created_at DESC, id DESC` の安定ソート）を採用する。**

### 3.5 カテゴリ絞り込み: サーバ側（Opus） vs 見送り（GPT） vs クライアント側タブのみ（Grok）

**判定: サーバ側（Opus）を採用。Grok のクライアント側フィルタは却下。GPT の見送りは次点として許容。**

ページネーションを採用する前提に立つと、Grok の「クライアント側タブでカテゴリを絞る」は成立しない。サーバから返るのは現在ページの50件だけであり、クライアント側でカテゴリを絞ると「総件数」表示と実際にタブに表示される行数が食い違う（Opus がこの矛盾を名指しで指摘している）。Grok 案はこの矛盾を「ページネーション無し」という前提の上でのみ回避しているため、3.4 でページネーションを採用する以上、3.5 も連動してサーバ側に決まる。

GPT 案（絞り込みを今回スコープ外にする）は矛盾を生まない安全な選択だが、issue の「埋もれ解消」という目的にとって絞り込みは低コストで価値がある追加なので、**Opus の「絞り込みとページングを同一コミットではなく別コミットで段階的に追加する」計画を採用**し、GPT の慎重さは「まず絞り込み無しの一覧を先に緑にする」という実装順序の考え方として汲み取る。

### 3.6 ヘッダーへの導線: 出す（Opus・推奨扱い） vs 出さない（GPT・Grok）

**判定: 出さない（GPT・Grok 側）を採用。Opus の推奨は保留。**

Opus はヘッダーに `is_admin` 分岐のリンクを出すことを「必須要件ではないが推奨」としている。しかしこれは `inertia_share` という全ページ共通の props に運営専用フラグを混ぜる変更であり、影響範囲が本 issue のスコープ（読み取り専用の一覧ページ1枚）を超える。実際に Opus 自身のリスク表（回帰ポイント1）も「`SharedProps` 型の更新漏れで `bun run check` が落ちる」を挙げており、必須ではない変更のためにこの種のリスクを取る必要はない。GPT・Grok はどちらも「URL 直打ち運用でよい」として見送っており、運営が1人という前提（3案共通の仮定）でも URL のブックマークで十分に運用できる。**今回は導線を追加しない。将来 URL を忘れやすいという運用上の実害が出たら、その時点で別コミットとして `auth.is_admin` を追加する。**

### 3.7 `has_many :feedbacks, dependent: :nullify` を今回入れるか（Grok が提案、Opus は「別issueへ」、GPT は言及なし）

**判定: 入れない。Opus の「発見事項として記録し別issueに切る」を採用。**

この関連は現在の一覧機能の実装に技術的に必須ではない（`Feedback.includes(:user)` は `belongs_to :user` だけで動く。逆関連は不要）。退会機能がまだ存在しないため実害もゼロ。Grok案はこれを「1行なのでついでに」と本 issue のコミットに含めているが、これは**この issue が閉じるべき問題（読み取り専用ページの新設）と無関係な、将来のリスクへの予防的パッチ**であり、レビュー観点の「やりすぎ」に該当する。Opus のように発見事項として記録しつつ実装は別 issue に切る方が、コミット単位の責務が明確になる。

### 3.8 「管理者」 vs 「運営」の用語（Opus は解消、Grok は認識しつつ放置、GPT は無言）

**判定: Opus の「CONTEXT.md に『運営』を正典として追記する」を採用。**

`domain-modeling` スキルは「ユーザーが使う語が既存の glossary と矛盾するときは即座に指摘する」「概念が glossary に無いなら、本当の穴として `/domain-modeling` へ引き渡すか、語を発明していないか確認する」と明示している。今回のケースは特殊で、**「運営」は既に `CONTEXT.md`「フィードバック」の定義文の中で使われている**（「プレイヤーがアプリ内フォームから運営へ送る連絡」）。issue タイトルの「管理者」はこの既存語と衝突する新語であり、これは「発明」ではなく「既存語が項目として未収載なだけ」というケース。

Grok 案はこの衝突に気づいていながら「まだ複数の運営ページが無いので canonize しない」と判断し、CONTEXT.md を更新しない。しかしこれは domain-modeling スキルの「用語が解決した瞬間にすぐ書く。バッチ処理しない」という指針に反する。すでに glossary の本文が使っている語を、項目として明文化するだけの作業であり、待つ理由が薄い。GPT 案はこの衝突自体に触れておらず、`変更モジュール`の表にも `CONTEXT.md` が一切現れない。これは3案の中で最も見落としが大きい点。**Opus の追記案（「運営」を正典にし、コード識別子は `admin` のままでよいとする）を採用する。**

## 4. 推奨する合成プラン

**Opus 案をベースに、以下の点だけ差し替える。**

1. **認可**: Opus のまま（`User#admin?` + `ENV["ADMIN_EMAILS"]`、`require_admin` を `ApplicationController` に、`require_login` の隣に置く）。
2. **非運営への応答**: Opus のまま（常に404）。
3. **一覧・絞り込み・ページング**: Opus のまま（サーバ側ページング50件 + カテゴリ絞り込み。コミットを分けて段階導入）。
4. **ヘッダー導線**: 入れない（§3.6 の判定どおり、Opus の推奨を採用しない）。今回のスコープから明示的に外す。
5. **`has_many :feedbacks`**: 入れない。R11 として記録し、別issueに切る（Opus のまま）。
6. **props の防御**: GPT 案の「管理ルートに `Cache-Control: no-store` を付ける」を追加で取り込む。共有端末で運営がログアウトした後もブラウザキャッシュに PII が残るリスクを一段減らせる、低コストな追加。Opus は `config.encrypt_history = true`（Inertia の履歴暗号化）で足りるとしているが、この設定はセッション暗号鍵に依存し、キャッシュそのものを消すものではないため、両方を重ねる方が保守的。
7. **ドメイン用語**: Opus のまま（`CONTEXT.md` に「運営」「フィードバック一覧」を追記、ADR-0011「許可リスト方式・ロール列を持たない・404で存在を伏せる」を1本書く）。
8. **`AdminAccess` への含み**: 採用しないが、ADR-0011 の「却下した代替案」に一行加える価値がある——「`User#admin?` ではなく独立 PORO `AdminAccess` に判定を置く案も検討したが、既存の `require_login` パターンとの一貫性を優先した。将来ドメインモデルが肥大化したら移行先として有効」。これにより Grok の設計上の懸念を無視せず記録に残す。

この合成の実装順序は Opus §5 のコミット単位（`CONTEXT.md`/ADR → `User#admin?` → UI（未接続） → ルート+認可+基本一覧 → 絞り込み → ページング → `no-store` 追加 → デプロイ配線）をそのまま使ってよい。各コミットが単体で緑・公開 `/feedback` を壊さない、という設計は3案の中で Opus が最も具体的に検証している。

## 5. ブロッカーと質問

実装着手前に解消すべき、または人間の判断が要る点。

1. **用語の最終決定**: `CONTEXT.md` に追記するのは「運営」で確定してよいか。issue タイトルは「管理者用」だが、既存 glossary 本文と一致させる Opus の判断（§3.8）を採用する前提で進める。ここだけは実装前に issue 本文か PR で明記した方が安全（後から見た人が「なぜ issue と glossary の語が違うのか」を追わなくて済む）。
2. **本番 `ADMIN_EMAILS` の投入**: 3案とも「実際の値の投入は人間の作業」としている。実装 PR がマージされてから `config/deploy.yml` / `.kamal/secrets` / credentials 編集を行うまでの間、本番では運営自身も 404 になる（fail closed の裏側）。デプロイ手順の順序（credentials 編集 → デプロイ）を `docs/deployment.md` に明記すること自体はブロッカーではないが、実際の投入作業を誰がいつ行うかは確認が必要。
3. **カテゴリ絞り込み・ページングを同一 PR に含めるか**: 3.4/3.5 の判定はサーバ側で行うことまでは決めたが、Opus のように段階的に複数コミットへ分けるか、GPT のように「一覧が動く1コミット」に絞り込みまで含めるかは実装者の裁量に委ねてよい。受け入れ条件（新しい順・全件到達・カテゴリ絞り込み）を満たす限り、コミット粒度はどちらでも良い。
4. **`Cache-Control: no-store` の適用範囲**: `Admin::FeedbacksController` だけに適用するか、`require_admin` を通る将来の全管理ルートに適用するかは、`require_admin` の実装（`before_action` 内で一緒にヘッダーを設定するか、別の `after_action` にするか）次第。次の管理ページが出来るまでは `Admin::FeedbacksController` 側に置いて構わない。
5. **51件以上のテストデータを作る factory コストが CI 時間に響かないか**: 3案とも request spec に51件超のケースを入れており妥当だが、`bundle exec rspec` 全体の実行時間が既存 CI のタイムアウトに影響しないかは軽く確認しておきたい（新規追加分は小さいはずだが、事実として未検証）。
