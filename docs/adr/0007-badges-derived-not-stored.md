# バッジは解除テーブルを持たず game_results から導出する

バッジ（実績・バッジ画面）の解除判定・解除日時・進捗は、`user_badges` のような解除テーブルに保存せず、毎回 `game_results` から導出する。カタログは全バッジの達成条件が `game_results` の既存カラム（回数・モード・難易度・スコア・タイム・正確率・WPM・最大コンボ・正解札数・日時）から判定できるものだけで構成し、これを前提に成立させる。解除日時も「条件を初めて満たしたプレイ」から導出する（100回プレイなら100件目の `created_at`、等）。

**理由**: ADR 0005 と同じく、「保存された解除」と「現在の条件で計算した解除」が食い違う経路を構造的に排除する。テーブル方式はゲーム完了時の書き込みフックと導入時バックフィルを要し、カタログ変更のたびに保存値と定義がずれるリスクを負う。

## Considered Options

- **(却下) `user_badges` テーブル（user_id / badge_id / unlocked_at）** — 「一度解除したら剥がれない」保証が得られるが、導出値との食い違い経路・書き込みフック・バックフィルのコストを伴う。開発段階でその保証に払う価値がない。

## Consequences

- **バッジは現行カタログに対する導出結果であり、カタログの閾値変更で遡って増減する（剥がれることもある）。** ベストスコアのクリーンカット（ADR 0005）と同種の、開発段階ゆえに許容した後退である。
- **導出期間中のカタログ変更履歴は残らない。** 「旧カタログでは解除済みだった」事実は復元できない。
- **将来テーブル化する場合は、その時点の導出結果（解除集合＋導出解除日時）を種蒔きして移行する。** `game_results` に欠損が無いため、ADR 0005 が却下したバックフィルと違い情報の欠けなく移行できる。
- 「解除の瞬間に通知」を将来やる場合も、プレイ前後の導出差分で実現できるため、テーブルは必須にならない。
